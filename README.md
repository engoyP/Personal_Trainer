# 个人运动分析与训练助手

拉取华为运动健康等来源的运动数据，计算心率、步频、步幅、配速、训练负荷等指标，再由 LangGraph 驱动的 Agent 生成训练/减脂计划。

## 架构

```
数据源 → 解析 → 分析引擎（纯代码） → [token 边界] → LangGraph Agent → 计划
```

核心原则：**LLM 不做算术，也永远看不到原始采样点。** 一次跑步有几千个采样点，全部由分析引擎压缩成约 30 个聚合字段后再交给模型。

| 层 | 位置 | 说明 |
|----|------|------|
| 解析层 | `backend/app/services/parsers/` | GPX / TCX / CSV / 华为 JSON，统一输出采样序列 |
| 分析层 | `backend/app/services/analytics.py` | 配速、心率区间、步幅、TRIMP 负荷、ATL/CTL/TSB |
| 知识层 | `backend/app/knowledge/` | 每周爬取权威运动训练健康文章，结构化入库，供 Agent 引用 |
| Agent 层 | `backend/app/agent/` | LangGraph 图：评估 → 规划 → 校验 → 修正 |
| 前端 | `frontend/src/views/` | Vue3 + ECharts 看板 |

### LangGraph 流程

```
load_context → assess → plan → validate →(通过)→ finalize
                          ↑                  ↓
                          └── revise ←──(不通过，最多 2 轮)
```

`finalize` 前设置了 `interrupt_before`，计划生成完会暂停等你确认。约束不靠 prompt 保证，而是由 `validate` 节点用规则引擎硬校验：

- 周跑量增幅 ≤ 近 4 周均值的 10%
- 每周至少 1 天完全休息
- 高强度（间歇+节奏）时长占比 ≤ 20%
- ACWR > 1.3 时强制减量
- TSB < −20 时禁止间歇/节奏/长距离
- 单次时长 ≤ 个人历史最长的 110%
- 减脂速率 ≤ 1.0 kg/周

## 训练知识库

每周一早上 8 点自动爬取一批权威站点的运动训练与健康文章，结构化入库，`plan` 与教练对话时会检索并引用。

**知识子图**（`backend/app/knowledge/graph.py`，独立可跑，也能当子图挂到主图上）

```
prepare → discover → crawl → extract → store → verify → report
```

- `discover` 发现候选链接后**按「像不像文章详情页」排序再取前 N 条**（不做 DOM 顺序截断 —— 那样只会拿到页顶导航），跨源去重
- `crawl` 并发抓正文（信号量限流 + 同域礼貌间隔），随后对正文里的图片做 **OCR 补文字**（见下）
- `extract` 调 LLM 抽出标题/机构/日期/主题/摘要/要点/证据等级，并判定 `substantive`。长文先分段再抽取再合并（见下）
- `store` 串行入库，三道闸门：目录页 / 机构新闻 / 主题相关，再按 URL 哈希去重
- `verify` 假成功自检。**按源**统计：抓到 ≥3 篇却 0 入库的源一定是列表页选错，会被标出来

**关键词搜全网**：知识页输入关键词（如「拉伸姿势教学」）→ 博查 Web Search API 发现
全网相关文章 → 走同一条抓取/抽取/入库链路。实测直接抓 Bing/百度/搜狗结果页都不可靠
（Bing 返回缓存无关内容、百度只给自家内容页、搜狗反爬），所以用博查结构化 API。
需在 `backend/.env` 配 `BOCHA_API_KEY`；不配则该按钮降级提示，不影响按源爬取。

搜索质量做了三层处理：① **多路搜索**（普通 + `site:gov.cn` + `site:nhs.uk` + `site:who.int`，
把权威内容捞进来）；② 结果**按域名权威分降序**（爬取按顺序取名额 = 权威优先抓）；
③ 低质站黑名单（文库/文档站/内容农场）。知识页另有「**仅权威源**」勾选
（`min_authority=0.85`），只收权威机构内容。

> ⚠️ 但**权威机构几乎不写「食材替换」「减脂餐搭配」这类生活化内容**，写这些的必然是门户。
> 所以关键词搜索能入库的天然是门户内容（权威分 0.5~0.55）。要高质量营养知识，
> 靠**定向权威源**（见下）而不是关键词搜索。

**权威源清单**（`app/knowledge/sources.py` 的 `SOURCES`）：运动训练类的 ACSM / Harvard Health /
NHS / WHO / 国家体育科研所 / 中国疾控 等，加上 2026-09-18 为「饮食计划」补的两个中文营养源：

| 源 | 域名 | 权威 | 说明 |
|---|---|---|---|
| 中国营养学会·膳食指南 | `dg.cnsoc.org` | 1.0 | 《中国居民膳食指南（2022）》官方站，营养领域最权威中文源 |
| 上海市疾控中心 | `scdc.sh.cn` | 0.95 | 只取「热点信息」栏目（健康科普），避开通知公告 |

> 实测过的取舍：北京疾控（栏目全是中心要闻/党建）、中国营养学会主站（反爬）、
> 国家卫健委（反爬）、广东省疾控（域名已易主）、中国疾控营养所（域名解析失败）都被排除。
> 加新源前用 `scripts/probe_candidates.py` / `probe_cols.py` / `probe_dg.py` 先实测。

**图片 OCR**（`app/knowledge/image_ocr.py`）：抓到的正文里若含图片，下载并用 EasyOCR
提取**图片上的文字**（图解、图注），追加进正文让抽取环节看到 —— 教学类内容的要点
常以图片呈现，纯文本抽取会漏。边界：EasyOCR 只能读图片里的文字，**看不懂姿势动作
本身**（那需要多模态模型）。每篇最多 `KB_IMAGE_OCR_MAX`（默认 3）张，OCR 服务不可用
时静默跳过。

**正文降噪**（`crawler.strip_leading_nav`）是这套东西能不能用的关键。crawl4ai 自带的 `fit_markdown` 剪枝不稳定（实测把 ACSM 的文章正文剪掉、留下侧栏推广块），所以改成确定性规则：找「正文行成团」的位置截断前置导航，再按页脚标记名截断后置样板。

**权威打分** = 域名权威 × 0.55 + 时效 × 0.20 + 主题相关 × 0.25

域名分取「后缀权重」与「站点白名单」的较大值，避免 `mayoclinic.org` 被通用的 `.com=0.5` 拖下来：

| 后缀 | 权重 | | 后缀 | 权重 |
|---|---|---|---|---|
| `.gov` / `.gov.cn` | 1.00 | | `.org` / `.org.cn` | 0.85 |
| `.edu` / `.ac` / `.ac.uk` | 0.95 | | `.com.cn` / `.cn` | 0.55 |
| `.int` | 0.90 | | 未知后缀 | 0.35 |

白名单里的机构（ACSM、NIH、Cochrane、BJSM、Mayo Clinic、国家体育总局、卫健委等）直接给 1.0。

**选源的教训（重要）**：中文官方站的**首页几乎全是机构新闻**（工作会议、党建活动、领导出访、资产公示），不能当抓取入口。英文源之所以能用，是因为它们的落地页本身就是主题枢纽页。所以中文源一律指向**科普/主题栏目**。`sources.py` 的 `DISABLED_SOURCES` 里记着一批「能抓到但内容不对」的源（国家体育总局、中华医学会、中国体育报、中国营养学会、人民网健康、中国体育科学学会、科普中国），附了停用理由，别再重复踩。

**一个源的多个栏目页共享 `max_per_source` 名额，且在栏目页之间轮转取**（`pipeline.discover_all`）。加新栏目页时要注意：按顺序取满的话，第一个栏目页（实测 `/physical-health` 有 40 条链接）会把名额吃光，后加的栏目页**永远轮不到**，而且不报错，只表现为「这个栏目一篇都没进来」。现在改成轮转，每个栏目页轮流贡献。**这个坑也是在补睡眠卫生栏目时才发现的**：Sleep Foundation 原来只抓 `/physical-health`，收进来的 10 篇全是疾病向（糖尿病/免疫/帕金森），问「怎么提高睡眠质量」只能命中这些；补上 `/sleep-hygiene` 后才进来 `How to Go to Sleep Earlier`、`What Causes Poor Sleep Quality?` 这类真对题的文章（⚠️ 别用 `/sleep-hygiene/healthy-sleep-tips`，那个入口带出一大批 `/best-mattress/` 带货页）。

**分层存储**：正文全文留在库里（`content_md`），但只把摘要与要点喂给模型 —— 和「LLM 看不到原始采样点」是同一条纪律。需要原文时前端单独展开，不进 prompt。

**长文分段抽取**（`extract._segment`）。这是"只喂摘要/要点"这条纪律的软肋：既然下游只看摘要和要点，那摘要和要点的**覆盖面**就等于这篇文章的全部可见度。

早期做法是正文超 5000 字就「头 4000 + 中间省略 + 尾 1000」，实测站不住 —— 库里有 64% 的文章超过 5000 字，最长 53,438 字，一篇 52,949 字的《Sleep and Immunity》有 **90.6% 的正文没进过模型**，中段的 `Sleep and Vaccines`、`Sleep and Allergies`、`How Can You Improve Sleep...` 全被丢掉，抽出来的要点只剩开头的泛泛过渡句。而这些中段话题在向量里根本不存在，检索自然召不回。

现在的做法分三步：

1. **先去噪再切** —— `_prose_only` 剔掉图片行和链接密集行（导航/相关阅读/参考文献链接）。噪声占比在长短文上差一个量级：全库 **p25 7.5% / 中位 22.7% / p75 57% / 最高 76.4%**，CDC 和 Sleep Foundation 那批带图长文普遍在 **59~76%**（《Can a Lack of Sleep Cause Nausea?》43,337 字去噪后只剩 11,567 字）。不去噪就切，25000 字预算会被噪声吃掉大半。
2. **按子标题边界切** —— 沿 `##` 切块，块内超限再按空行→句子降级切；`## References` / `相关阅读` / 编辑团队这类整块丢掉（全库占有效正文 6.3%，在 Sleep Foundation 那批长文里能独占一整段）。段数上限 `MAX_SEGMENTS=5`、每段 `SEG_CHARS=5000`，超长文等间隔抽样，保证覆盖均匀而不是留头砍尾。
3. **合并** —— 各段结果交给一次合并调用，要求归并去重、优先保留带具体数字的条目、摘要覆盖各段主要话题。合并失败有确定性兜底（挑要点最多的一段当底，其余要点并进来）。

效果：去掉参考文献后的正文覆盖率**中位 100%、最低 99%**，而送模型的总字数只涨 **1.5 倍**（1.5 倍而不是 5 倍，是因为去噪省下的量刚好抵掉多段开销）。同一篇《Sleep and Immunity》，要点从"免疫系统很重要"式的 4 条，变成带具体数字的 6 条（疫苗有效性下降、花生过敏阈值降 45%、N3 深睡与 REM 抑制）。短文（有效正文 ≤5000 字）仍走单次调用，行为完全不变。

改了抽取策略后**历史文章不会自动受益** —— 摘要/要点只在爬取时抽一次。用 `scripts/reextract.py` 重跑（默认只重抽被截断的那批，自动连带重算向量）。

**相关度必须在散文上算**：导航菜单和页脚友情链接里全是主题词（一个医学会页脚列着"运动医疗分会""肠外肠内营养学分会"），会让《报废固定资产处置公示》算出 0.42 的相关度。所以判相关度前先剔除导航行、按页脚标记截断，另外用标题形态挡掉机构新闻（会议/通知/公示/征文）。

**依赖隔离说明**：crawl4ai 依赖的 litellm 要求 `openai>=2.8`，会连带升级项目里的 openai。抓取层做了双后端，`Crawl4AIBackend` 不可用时自动退到 `SimpleBackend`（httpx + 正则），保证知识库不会因为浏览器内核装不上而整体瘫痪。

**双后端是两级的，别只做一级**：光在「整轮开始时挑后端」不够 —— 实测 ACSM 一轮 8 篇里 **4 篇 playwright 导航失败**（`Failed on navigating ACS-GOTO`），而后端是整轮只选一次的，这 4 篇就白白丢了；每周任务无人值守，跑空一轮等于白等一周。所以 `pipeline.fetch_batch` 里还有**逐 URL 降级**：crawl4ai 对某个 URL 失败时，用 httpx 再补抓一次（JS 渲染站可能拿不到正文，但比整篇丢掉强）。补抓的篇数会出现在爬取报告的「观察」里，数字突然变大说明浏览器后端在退化。

**检索用的是本地语义模型**（`Qwen3-Embedding-0.6B` + `Qwen3-Reranker-0.6B`，权重在 `D:\models\Qwen`），不调外部 API：

```
问题 ──▶ 向量召回（余弦 top-30，关键词命中补位）
      ──▶ 重排精排（yes/no logit 差，≥ 阈值才留）
      ──▶ 按「重排 0.7 + 权威 0.3」排序 ──▶ 摘要与要点
```

- 模型跑在**独立的本地服务**里（`scripts/model_server.py`，默认 `127.0.0.1:8100`），用带 CUDA 的解释器启动。后端通过 HTTP 调用，**服务没起 / 超时 / 报错一律静默退回关键词逻辑** —— 语义能力是增强不是依赖，一个本地服务没开不能让整个问答瘫掉。返回的 `via` 字段会标出走了哪条路（`semantic` / `keyword`）。
- **召回**单元是整篇文章（没有 chunk 切分，一篇 = 一个向量）；**重排**单元是文章的**要点**（见下）。

**重排按要点打分，取最大**（`retrieve._probe_ranks`）。交叉编码器是「(查询, 段落) → 一个分数」，整篇喂进去时分数被主话题主导。《Sleep and Immunity》六条要点里五条讲免疫/疫苗/炎症、只有一条讲睡眠卫生，问「怎么提高睡眠质量」时整段只有 −6.02（被 −1.0 的阈值挡掉），而单独打那一条睡眠卫生要点是 +4.34。一篇文章只要**任何一条要点**能回答查询就该判为相关，所以拆开打分、每篇取最大值（`MAX_POINT_PROBES=8`，抽取侧上限也是 8）。

四个坑（都是实测踩出来的，细节见 `semantics.py` / `model_server.py` 注释）：

1. **查询侧不要加 instruction**。官方写法是给查询加 `Instruct: ...\nQuery: ...`，但这个权重副本加了以后**排序会变反** —— 直接跑官方 model card 的例子，加 instruction 时"法国首都"会排到"中国首都"前面，不加才正确。去掉后召回质量跃升（目标文章从「余弦排 51/75」变成「排 1/75」）。`QUERY_INSTRUCT` 默认空串。
2. **重排文本不放标题**。同一篇文章，`标题+摘要` 给 −9.32、`仅摘要` 给 −2.97，英文标题尤其致命。阈值是绝对分，这一项直接决定文章能不能进结果。向量侧反过来（带标题更好），所以两边各用各的文本。
3. **阈值靠实测标定**，`RERANK_KEEP=-1.0`。实测（80 篇、10 条该命中 + 4 条该为空）真命中 +1.19~+5.73、擦边 −2.6~−3.7、无关 −8.19 以下，取 −1.0 落在空档中间。重排分是绝对分，换模型或改指令都要重新标定 —— 用 `scripts/eval_semantics.py` 跑。
   回归集里的 3 条睡眠查询是**专门锁回归**的，它们曾经全部返空且原因各不相同（重排被主话题淹没 / 抽取窗口吃掉中段 / 内容来自恢复的中段），任何一处回退这里就会红。
4. **重排必须传 `logits_to_keep=1`**（`model_server.rerank_pairs`）。只取末位 yes/no 判定，却默认给**每个位置**都算 151936 维词表 logits：batch=32 × 112 长度 × 151936 × 4 字节 ≈ **2.2GB**，而 4GB 显存的卡上 embed + rerank 两个模型已占 2.4GB，这块临时张量放不下，显存分配器反复腾挪。实测同一批 398 条要点：不加 53s，加了 9.85s —— **慢 5 倍全是这块显存闹的**，跟模型本身无关。

**重排的开销是「条数 × 每条 token」，两条优化都不能省**：

- **不把摘要当重排单元**。摘要有 1000+ 字，混进短要点批里会把整批 padding 到它的长度（`_article_parts` 只用要点，摘要只在要点缺失时兜底）。
- **按 token 预算装箱，批内长度接近**（`RERANK_BATCH_TOKENS=2048` / `RERANK_CHUNK_MAX=16`）。批太小 GPU 空转，太大 padding 浪费：实测同一批 398 条，batch=16 用 5.6 万 token、batch=64 用 6.5 万。

端到端（RTX 3050 Laptop，75 篇 / 398 条要点，召回池 30~40 篇 → 约 185 对）：单次查询 **3.2~4.3s**。修 `logits_to_keep` 之前是 9~11s。

⚠️ 别想着「少重排几篇」来提速：实测过给重排条数设预算，预算 64 条（只覆盖 12/30 篇）时 12 个查询里有 7 个的 top-5 结果集就变了。也别想着「用向量余弦给要点做粗筛」：双编码器在这个粒度上不具判别力，问「怎么提高睡眠质量」时余弦 top-8 全是泛运动文章、重排 top-5 全是睡眠文章，余弦 top-40 只能捞回 2/8 条真正相关的要点。同理召回池也不能砍 —— 有查询的最佳答案在余弦榜上排到第 43 位。

**入库闸门不用语义**。试过用「文章 vs 主题原型」的重排分做入库否决，但绝对分不校准（宽泛原型查询会压低所有分数，-6 的线会误杀 48/75 篇文章）。所以语义只用在对**具体问题**做检索排序，入库继续交给可解释、可回归的确定性规则。


## 训练计划与饮食

生成计划时**同时产出饮食安排**（减脂场景尤其需要），方案是「**数字由代码算，执行建议由 LLM 给**」：

- `app/services/nutrition.py`（纯代码，LLM 只读不准改）：Mifflin-St Jeor 基础代谢 →
  活动系数（按每周训练天数）→ TDEE → 减脂缺口（默认 −400 kcal，**且不低于 BMR×1.1**，
  低于基础代谢会掉肌肉）。
- 三大营养素：蛋白质 1.8g/kg（减脂保肌下限，不从蛋白扣热量）、脂肪 max(0.9g/kg, 总热量 20%)、
  碳水吃剩余。缺体重/身高/年龄时返回 `available=False`，不硬编数字。
- LLM 只负责：执行原则（每餐先吃蛋白和蔬菜、训练日碳水前移等）+ 训练日/休息日三餐示例。
  **营养数字由 `_apply_nutrition()` 在 plan 和 revise 两个节点兜底写回**，防止模型自造热量/克数。
- 减脂目标时，检索 query 会额外带上「减脂饮食 营养搭配 食材热量」——否则检索全被训练类
  文章占满，捞不到知识库里的营养条目。
- 实测（22岁男 / 180cm / 73.1kg / 减脂 / 每周 4 天）：BMR 1751 → TDEE 2714 →
  目标 **2314 kcal**，蛋白 132g / 脂肪 66g / 碳水 298g，缺口 400 kcal。

### 食材替换（对话里问）

计划里的食材家里没有时，直接在教练对话里说「XX 我没有，能换什么」：

- 回答**按营养等价**给替代（热量与主要营养素相近、优先同类食材），能引用知识库就引用；
- 检索 query 检测到「没有 / 换成 / 替换 / 买不到…」时自动补营养词，否则检索容易被
  训练类文章带偏（用户问题里没几个营养词）；
- 对话上下文会带上**营养目标 + 最近一次饮食计划**，教练据此判断替换是否影响缺口；
- 知识库里没有对应条目时，教练会明说「这不是引用」，不硬凑。

> ⚠️ 相关坑：`MODEL_RERANK_KEEP` 原为 `-1.0`，是按 80 篇**训练类**语料标定的。
> 知识库补进饮食/替换类文章后，这类内容的 rerank 分系统性偏低（真命中才 -1.9~-2.4），
> `-1.0` 会把它们全挡掉 —— 表现为「明明有对口文章却 0 命中」。已下调到 **-2.5**
> （饮食类能捞回、训练类不受影响、无关查询仍 0 命中）。改模型或大改语料组成后要重标。

> CUDA context 一旦初始化 ~1.2GB，进程退出前无法释放（torch 硬约束），会挤掉 rerank
> 导致生成计划卡死。所以默认 `OCR_CUDA=0`（CPU）；想 GPU 加速就改 `1`，但需先停 8100。
> OCR 已做成懒加载：启动不加载模型、首次识图才加载、空闲 10 分钟自动释放。

## 数据导入

| 来源 | 方法 | 备注 |
|------|------|------|
| 华为运动健康·**单次运动明细**（推荐） | 运动记录 → 打开某次运动 → 分享/更多 → **导出数据** | 逐点 CSV，含时间/心率/配速/步频，**唯一能拿到心率的单条入口** |
| 华为运动健康·单次轨迹 | 运动记录 → 打开有轨迹的户外锻炼 → 右侧轨迹图标 → 导出路线文件 | 得到 GPX/TCX/KML，**只有轨迹，不含心率和步频** |
| 华为运动健康·全量 | 华为账号 → 隐私中心 → 请求你的数据 → 勾选健康 → 等邮件下载 ZIP | 历史全量，1-7 天到手；一个 JSON 目前只导入一条 |
| 华为运动健康·每日汇总 | 我的 → 运动数据 → 导出 | CSV，但**每天一行**，没有逐点数据，**无法导入** |
| 手动录入 / 识图录入 | Profile 页「手动录入运动」 | 只有 summary 截图/无文件时填日期、距离、时长、心率等；「📷 从截图识别」用 EasyOCR 抽字段预填，**不伪造逐点心率** |
| Keep | 前端暂未接入 | 适配层已预留 |

导入前可以先点「先看结构」确认字段识别是否正确，尤其是华为导出的 JSON 和 CSV。

改了体重或最大心率后，记得点「按当前档案重算历史数据」，负荷和卡路里会跟着更新。

### CSV：两种 CSV 只认其中一种

华为的 CSV 有两个来源，性质完全不同，**必须区别对待**：

| 来源 | 形态 | 能否导入 |
|------|------|----------|
| 单次运动 → 分享/更多 → 导出数据 | 逐点（时间 / 心率 / 配速 / 距离 / 步频），每秒一行 | 可以，且**含心率** |
| 我的 → 运动数据 → 导出 | 每天一行（日期 / 步数 / 卡路里 / 运动时间） | **不能**，没有逐点数据 |

把汇总表硬当采样序列算，会得到一条「0 km、时长几秒」的假记录 —— 不报错，直接落库。
所以解析器（`parsers/csv.py`）加了五道闸门，每条都对应一个踩过的坑：

1. **表头不一定在第一行**。华为导出的 CSV 前面常有「标题 / 导出时间 / 运动类型」几行说明，
   按「第一行就是表头」取会一个字段都认不出。现在在前 10 行里挑匹配字段最多的那行当表头。
2. **时间列认三种写法**：`2026-09-05 11:45:33`、`1:02:03`、`330`（秒），以及 Unix 时间戳。
   以前只认纯秒数，遇到日期字符串直接 `ValueError` → 接口 500。
3. **时间轴必须单调不减**。汇总表（每天一行，时长忽长忽短）和列被认错的情况会立刻违反。
   另有日期跨度检查：一张表覆盖 ≥3 个不同日期，就是汇总表，直接拒绝并给出可操作的下一步。
4. **只有相对用时的 CSV 会给告警**。没有日期就没有 `start_time`，而 `start_time IS NULL`
   的记录会被 `start_time >= since` 直接排除 —— 它进不了 ATL/CTL 曲线和趋势统计，
   也无法参与重复检测。这种情况不编造日期，明说它进不了负荷曲线。
5. **里程来源缺失时也会告警**。里程只能从速度 / 配速 / 经纬度算出来；三者都没有时
   （比如只有「时间 + 心率」，或只有一个「距离」列）距离必然是 0，落库会得到一条
   「0 km 但有负荷」的记录。这种情况直接说出来，不让人以为是导入出错。
   ⚠️ **「距离」列目前不参与计算**，因为没见过真实样本、无法确定它的单位是米还是公里，
   猜错就是 1000 倍误差 —— 与其猜，不如明说不算。见「已知问题」。

列名匹配也修了一个静默错误：别名里的 `t` 用子串匹配会命中 `HeartRate`（含字母 t），
于是**时间轴取的是心率值，时长被算成几秒**。现在单字符的 latin 别名只认全等，
并且同一列不会被两个字段抢。

运动类型从说明行或专门的列里嗅（`户外骑行` → `cycling`），认不出才退回默认 `running` ——
所以 `guess_sport` 之外多了个 `guess_sport_strict`，用来区分「认出来了」和「什么都没认出来」。

### 华为 GPX/TCX 没有心率，负荷怎么算

实测确认：华为「导出路线文件」是**纯轨迹导出**，GPX 和 TCX 内容完全等价，都只有
经纬度 / 海拔 / 时间戳，`HeartRateBpm` 和 `Cadence` 一个都没有（换格式也救不了）。
所以这类导入**心率区间必然是空的**。

训练负荷不跟着摆烂，分三档，每档都在数据里标了来源（`load_source`）：

| 情况 | 负荷 | `load_source` |
|------|------|---------------|
| 采样点有心率 | Banister TRIMP（实测值） | `trimp` |
| 无心率 | 配速 → MET → %HRR → 走同一套 TRIMP（估算值） | `met_estimate` |
| 档案本身无效（最大心率 ≤ 静息心率） | 不计算 | `none` |

估算用的是 `%HRR ≈ (MET−1)/(MET_max−1)`，`MET_max` 由 `VO2max = 15 × (最大心率/静息心率)`
折算。它和 TRIMP **量纲一致**，可以直接混在 ATL/CTL 曲线里 —— 实测一条 5.6 km / 配速 6:10 的
轻松跑，估算负荷 51.4，等价于平均心率 145 时的 TRIMP 51.1。

**估算值绝不冒充实测值**：详情页在负荷为估算时会显示橙色提示卡，`/api/activities`
每条都带 `load_source` 字段。想换成真实值，到华为 App 抄一眼平均心率，在详情页
「补填心率」里填进去（`POST /api/activities/{id}/heart-rate`），负荷立刻切成 TRIMP；
传 `null` 可以清空回退到估算。补填只改汇总值，**不会拿一个平均值编造逐点心率分布**，
心率区间仍然留空。

`/api/analytics/recalc` 会保留手工补填的心率（判断依据：采样点里没有任何心率，
但汇总上有平均心率 → 只可能是手工填的），不会一次重算就抹掉。

**估算这件事会一路传到教练**：`build_metrics` 额外算 `hr_missing_ratio_28d` 和
`estimated_load_ratio_28d`，教练的两条路径都会拿到 ——

- **计划评估**（`nodes.assess`）：提示词里加一行「近 28 天 X% 的负荷是估算的，据此判断请留有余地」。
- **教练对话**（`chat.build_context`）：指标是整包 JSON 丢给模型的，光有
  `estimated_load_ratio_28d: 1.0` 这种键名模型并不知道该收敛结论，所以额外拼一段
  **自然语言**的【数据质量】说明。

计划校验里 `acwr > 1.3` / `TSB < -20` 是**硬拦截**，估算占比 ≥30% 时会在拦截理由后面
追加一句说明。**闸门不会因为数据不确定就放松** —— 放松等于拿不确定性去冒受伤风险 ——
但必须让人知道这条拦截的分量有多重。

实测效果（问「我最近负荷有点高，这周还能加量吗」），教练在结论后主动补了一句：
「14% 的运动缺心率、10% 负荷是配速估算的，所以 ACWR 这个 2.43 有误差，但趋势方向不会错」。

### 时间戳时区：`Z` 是 UTC，入库前换算成本地时间

华为导出的 GPX / TCX，时间戳都长这样：

```
<time>2026-09-05T11:45:33.000Z</time>          GPX
<Id>2026-09-05T11:45:33.000Z</Id>              TCX
```

`Z` 在 GPX 规范里表示 **UTC**。**实测确认过**：同一天那条跑步，华为 App 显示的
开始时间是 **19:45**（北京时间），而文件里写的是 **11:45Z** —— 正好差 8 小时。

原来 `_parse_time` 是 `fromisoformat(...).replace(tzinfo=None)`，即丢掉偏移量、
保留钟面数字，于是 **所有 GPX/TCX 导入的时间都早 8 小时**。影响面不只是显示：
**跨凌晨的运动会被归到前一天**，而 ATL/CTL 是按 `start_time.date()` 分桶的，
日负荷会跟着挪到错的日期。

修法是把时间解析收敛到 `backend/app/services/parsers/timeparse.py`，GPX / TCX / CSV
三个解析器共用一套口径：

| 文件里的写法 | 处理 |
|---|---|
| `2026-09-05T11:45:33.000Z` / `...T11:45:33Z` | 按 UTC 换算成本地 → `19:45:33` |
| `2026-09-05T11:45:33+08:00` | 按声明的偏移换算（这里是本地，值不变） |
| `2026-09-05T11:45:33-05:00` | 按偏移换算 → 次日 `00:45:33` |
| `2026-09-05T11:45:33`（**没有**时区标记） | **当本地时间，不换算** —— 文件没写时区就不能猜 |
| `1693900000` / `1693900000000` | 按 Unix 秒 / 毫秒（UTC）换算 |
| `330` / `1`（相对秒数） | **不当时间戳**，交给上层按 elapsed 处理（否则会变成 1970-01-01） |

时区用配置里的固定偏移 `LOCAL_UTC_OFFSET_HOURS`（默认 `8`），**不用 `zoneinfo`**：
中国自 1991 年起没有夏令时，+8 是精确的；而 Windows 上 `zoneinfo` 需要额外的
`tzdata` 包（本机没装），依赖宿主系统时区又不可移植（换台机器就变）。**换时区只改这一行。**

### 手动录入（无 GPS 文件 / 只有 summary 图）

华为室内运动、跑步机、或某些只给分享海报的场景没有轨迹文件。本项目提供两条路：

1. **识图录入（轻量 OCR）**：Profile 页「手动录入运动」卡片里的**拖拽区**（拖入图片或
   点击选择文件），把华为分享海报/截图发给本地 EasyOCR（`ch_sim+en`，GPU）识别，
   抽汇总字段自动预填表单，**你核对确认后再点「录入运动」落库**。只抽汇总字段
   （距离/时长/心率/步频/步幅/爬升/卡路里/日期时间），**不伪造逐点心率**——
   识别结果不直接落库，必须人工过一眼。
2. **纯手动录入**：OCR 服务没起时也能直接用表单填。

- 必填：运动类型、日期时间、距离（km）、时长（分钟）
- 选填：平均心率、最大心率、平均步频、平均步幅、累计爬升、卡路里
- 接口：`POST /api/activities/manual`（手动）、`POST /api/activities/recognize`（识图，返回字段不落库）

**实测准确率（两张真实华为海报，130+ 文本块/张）**：核心字段 10/10 全对——
距离、时长（含 `HH:MM:SS` 三段）、平均/最大心率、步频（`99171步` 数字粘连可拆）、
步幅（厘米转米）、卡路里、开始时间。解析层对华为海报的版式做了针对性处理：
两列卡片「标签上/值下」用 bbox x 对齐匹配、`2026/9/519:45` 无空格粘连（1 位日被
贪婪匹配吞掉时间首位时自动回退）、冒号误成点号、`M月D日` 与 `YYYY/M/D` 两种日期格式、
纯单位块（「次1分」「步1分」）跳过。已知局限：OCR 引擎偶发字符级漏字（如
`15.0米` → `1.5米`，置信度还很高），解析层无法防，**落库前务必核对爬升等小字段**。

**不会伪造逐点心率**：录入后没有 `activity_samples`，心率区间保持为空。
负荷分档和文件导入完全一致：

| 情况 | 负荷 | `load_source` |
|------|------|---------------|
| 填了平均心率 | Banister TRIMP（实测值） | `trimp` |
| 没填平均心率 | 配速 → MET → %HRR → 同一套 TRIMP（估算值） | `met_estimate` |

去重规则和文件导入一样：同一 `start_time` + `sport_type` 视为重复。
想修改已录入的心率，仍可调用 `POST /api/activities/{id}/heart-rate`。

### 去过的地方（地图点亮）

页面 `/places`：把跑过的城市在腾讯地图上点亮成金色光点，视野自动收拢到所有点亮城市。

- **添加**：页面顶部搜索城市名 → 点候选即可点亮；也可以在运动详情（`/activity/:id`）
  的「去过的城市」卡片里标记，会自动带上这次运动的日期作为首次达成时间。
- **数据**：内置 80+ 中国主要城市库（省会 + 主要地级市，GCJ-02 坐标，含港澳台），
  不依赖外部接口，离线可用。城市名唯一，重复标记累加 `visit_count`。
- **接口**：`GET /api/places/cities?q=`（搜索）、`GET/POST /api/places/visited`、
  `DELETE /api/places/visited/{id}`（取消点亮）。
- **隐私**：只存城市级坐标，**不存逐点轨迹**；个人位置数据仅本地私有存储，不外传。
- **地图不可用时的降级**：地图服务没加载时（离线/代理未生效），页面退化为城市列表，
  添加和统计照常可用——和轨迹图的降级策略一致。

原来的「我的路线」（多轨迹叠加）已移除；单次运动的轨迹图仍在详情页保留。

### 跑鞋（`/shoes`）

记录每双跑鞋陪你跑了多少公里：

- **录入**：鞋名 + 品牌 + 购入日期 + 购入时已有里程（`initial_km`）+ 备注，每双鞋可传一张照片。
- **记跑量**：每双鞋按日期手动记公里数，累计里程 = `initial_km` + Σ 跑量；跑量明细可展开、误记可删。
- **编辑**：卡片「编辑」弹窗改鞋名/品牌/购入日期/初始里程/备注，可标记「已退役」（退役鞋置灰）。
- **数据**：表 `shoes` / `shoe_mileages`；图片存本地 `data/shoe_images/`，经 `/api/shoes/{id}/image` 读回，不依赖外部存储。
- **接口**：`/api/shoes`（列表/建/PATCH 编辑/删）、`/api/shoes/{id}/image`（传/读图）、
  `/api/shoes/{id}/mileage`（记/查跑量）、`DELETE /api/shoes/mileage/{id}`（删单条跑量）。

### 首页运动日历

数据看板顶部嵌一个月历：默认当月，每天在日期下显示当天运动标签（如「跑步 5km」），
点击标签跳转到该次运动详情。数据来自 `GET /api/activities/calendar?year=&month=`（按月聚合）。

## 已知问题

- 华为 Health Service Kit 官方 API 要求应用上架华为应用市场才能申请权限，个人自用走不通，所以走文件导入。适配层已预留，权限批下来加个 provider 即可。
- Keep 无官方开放 API，只有非官方接口，暂未接入。
- uvicorn `--reload` 在本机（WatchFiles）不稳定，改完代码手动重启后端。
- 知识库的源会静默失效：站点改版、栏目迁移、反爬加严，都表现为「发现 0」或「抓到却 0 入库」，不报错。`verify` 节点会**按源**把这个情况标出来（`N 个源抓到≥3篇但0入库`），定位用 `scripts/diag_source.py`，改完源清单用 `scripts/probe_sources.py` 回归。
- 中文源只有 3 个（体育科学研究所、中国疾控、丁香医生）。不是偷懒：中文官方站首页普遍是机构新闻，实测筛选过 7 个源都因「没有可用的科普栏目」被停用（见 `DISABLED_SOURCES`）。要扩中文源，关键是找到**主题栏目页**而不是首页。
- Sleep Foundation、丁香医生这类站点在内容页里做导购引流，列表里混着商业测评（`/best-mattress/…`）。已按联盟营销路径过滤，但新源接入时要注意同类问题。
- **语义服务要手动起**（`scripts/model_server.py`），没有做自动拉起。它不在时知识库照常工作，只是退回关键词路径，检索结果里 `via` 会显示 `keyword`。
- **检索粒度是整篇文章**，一篇长文里靠后的细分内容会被单一向量稀释；而且**摘要质量直接决定向量质量** —— LLM 抽取降级时摘要退化成正文前 280 字，检索会跟着变差。
- 本地模型在 4GB 显存上必须分批推理（服务内已按 `RERANK_CHUNK=8` / `EMBED_CHUNK=16` 切开），一次送 75 篇以上会 OOM 返 500。
- **GPX/TCX 的 `Z` 时间戳按 UTC 换算成本地时间**，偏移在 `config.LOCAL_UTC_OFFSET_HOURS`
  （默认 8）。**没有时区标记的时间戳一律当本地时间，不做换算** —— 文件没写时区就不能猜。
  详见「数据导入」章节的时区小节。换时区或换机器时注意这一行是硬编码的偏移，不是 IANA 时区。
- **华为导出的 GPX/TCX 不含心率和步频**，这是实测结论（不是配置问题），所以心率区间对这类导入永远是空的，训练负荷走配速估算。详见「数据导入」章节。
- **CSV 的「距离」列不参与计算**。里程是从速度 / 配速 / 经纬度算的，距离列被忽略；
  只有距离列的文件会得到一条 0 km 记录（有告警，不静默）。要支持它得先确认单位（米还是公里），
  而这要靠真实样本 —— 猜错是 1000 倍误差，比不算更糟。
- **华为「单次运动 → 导出数据」的 CSV 还没拿到真实样本**。有第三方教程称它包含时间与心率列
  （那将是单条导入里唯一带心率的格式），解析器已按逐点 CSV 支持并加了五道闸门，
  但**只在合成的等价样本上验证过**，不能用真实华为文件背书。拿到样本后要做的第一件事是：
  数一下 `HeartRateBpm` / 心率列到底有没有值，并核对距离与华为 App 显示是否一致。
- **华为全量数据导出的 JSON 一个文件只导入一条活动**：`parse_huawei` 会挑采样点最多的那条。
  这个限制**不再静默** —— 导入结果会带 `warning` 说明「识别出 N 条可用运动，本次只导入了 1 条」，
  前端会显示出来。真正支持批量导入要改 `parse_file` / `ingest_bytes` 的单条契约，
  改之前得拿真实的华为导出样本验证，不靠猜。
  顺带一提：**GPX/TCX 都拿不到心率，JSON 确定可以**（华为全量导出里每个 JSON 文件对应一条运动是设计如此，
  不是丢数据）。CSV 是否也能拿到，见上一条待验证项。
- **室内运动/跑步机/只有 summary 海报的场景**：走 Profile 页「手动录入运动」。
  现在支持「📷 从截图识别」用 EasyOCR 自动抽汇总字段（服务没起时退化为纯手动填写），
  识别结果展示核对后再落库——不静默、不伪造逐点时序。OCR 对设计海报的准确率有折扣，
  关键数字落库前务必人工核对一遍。
- gpxpy **不解析 GPX 1.0 的 `<trk><type>`**（1.1 才读），华为导出的恰好是 1.0，所以运动类型是从原始 XML 里自己捞的（`parsers/gpx.py::_type_from_xml`）。换 gpxpy 版本时注意别把这条兜底弄丢。
